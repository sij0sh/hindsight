# Critical design review and implemented decisions

Reviewed inputs: the supplied `improvements.md` and `implementation-plan(1).md`, against the v0.1.0 implementation. The main architectural recommendation is sound: durable records should be canonical, with deterministic Markdown projections. The following corrections make that direction safer and more precise.

| Gap or risk in the supplied plan | v0.2.0 decision and implementation |
| --- | --- |
| Rejecting all compound statements suggests a semantic guarantee regex cannot provide | Validate one-paragraph structure and size; require atomicity review in the curator checklist. Valid conjunctions are allowed. |
| Dual Markdown/memory submission preserves two competing authorities | Cut over to memory-only submission. Preserve command compatibility, explicit migration, and recovery of old journals. Tests were updated instead of retaining the old writer. |
| Importing prose as immediately usable inferred memory could promote stale policy | Import as unverified candidates, retain exact originals and offsets, and require archive reading, scope/atomicity review, and fresh evidence before activation. |
| Near-duplicate auto-merging can erase negation, exceptions, or scope | Merge only exact claim/scope/kind/basis matches. Near matches remain a semantic review task. |
| “Session decision” does not distinguish a user instruction from assistant speculation | Derive provenance from actual message roles. Assistant claims cannot establish authority. |
| An ADR file or a mention of acceptance is not an accepted decision | Require explicit accepted status metadata and decision classification. ADR proposals remain proposals; resolution is a later operation. |
| Code drift could silently rewrite policy | Require current authoritative evidence to supersede, retire, or restore authoritative claims. Observed behavior has a separate basis. |
| Blocking all writes would also discard the proposed durable conflict | Permit blocked attempts to persist conflicts/disputed views, while retaining pending work and old source/session baselines. |
| A narrowly scoped conflict can hide a broadly scoped contested rule | Inherit all target scopes; suppress contested claims from normative retrieval and expose the conflict throughout their applicability. |
| “Atomically” writing several files overstates filesystem guarantees | Use a recoverable multi-file journal, preflight every target before replay, refuse pending-journal reads, and document visibility/race limits. |
| Regenerating a sibling document could be mistaken for completing its review | Update its generated-view fingerprint only; retain its source/session/memory baseline and queue reinspection. |
| A memory's evidence might live outside registry input globs | Add scope and source-provenance paths to domain routing; newly unread surface expansions remain pending. |
| Scar disappearance signals cannot prove business compatibility | Route explicit removal review using bounded inventory signals. Never auto-retire. Keep non-scar maintainability records too. |
| Substring symbols/concepts produce unrelated context | Use exact symbols, case-insensitive exact concepts, and path globs with explicit global scope. Report truncation and pending reviews. |
| Archiving retired records out of snapshots can break audit and links | Cap the whole ledger, including audit/tombstones. Fail visibly; defer automatic archival until link/provenance retention is designed. |
| ULIDs would add implementation/dependency surface without a ordering requirement | Use host-generated UUID-based IDs; use deterministic hash IDs for migration. Views have explicit stable sorting. |

## Delivered scope

The implementation includes the canonical ledger and validators; pure lifecycle reconciliation; one record projected into several domains; evidence-derived confidence; tombstones and audit lookup; scars and review signals; first-class conflicts with ADR references; deterministic ten-domain views and AGENTS routing; scoped CLI/Pi retrieval; opt-in context injection; guarded multi-file recovery; and explicit idempotent migration.

The existing deterministic router, 138 domain criteria, eight common criteria, bounded derived checks, Pi SDK isolation, read receipts, Git-layer handling, session batching, process locks, and per-domain queues remain in place. One additional memory reconciliation check covers scope, atomicity, duplication, currency, conflicts, and scar conditions.

## Validation-driven changes

Integration testing exposed an unnecessary second review when a new claim added already-read evidence to a domain's surface. The engine now acknowledges the expanded surface only if the added evidence was fully inspected. A separate regression ensures unread expansions still receive another review.

Migration testing also hardened list-item separation, CRLF preservation, repeated imports, and manually edited generated views. Lifecycle tests exercise authority guards, exact deduplication, history, conflict restoration, scoped retrieval, and source-layer independence. Recovery tests cover partial commits and a late-target edit that must stop replay before any earlier pending target is written.

## Remaining work and limitations

The real installed Pi SDK and live provider checks remain release gates: the build environment cannot install the pinned npm package. Mocked SDK tests establish adapter behavior, not actual package compatibility. Run `test:sdk`, then `test:live`, and review real output before relying on automatic curation.

Semantic atomicity, whether two claims mean the same thing, and whether evidence supports a claim are not mechanically proven. Source receipt ranges provide traceability, not entailment. External claims require supplied authoritative evidence because isolated curators cannot browse.

Migration is intentionally a conservative text importer, not a lossless semantic parser. A long paragraph or complex nested list may require explicit replacement into several claims. Full originals remain available. The stored `candidate_for_removal` scar state is reserved; v0.2.0 emits removal candidates in routing without mutating the ledger automatically.

Context injection recognizes simple explicitly mentioned known paths; quoted paths containing spaces should use `/knowledge context`. No task-intent inference, symbol resolver, embedding search, AST dependency graph, automatic ADR acceptance, or lossy audit archival is included. These are deliberate bounds, not completed capabilities.

For the next iteration, prioritize real-model evaluation over adding heuristics: measure unsupported active claims, missed explicit decisions, duplicate memories, conflict recall, and unnecessary repeat investigations on representative repositories. Then consider explicit audit archival and language-aware scope expansion with dedicated evidence fixtures.
